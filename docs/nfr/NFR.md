# Нефункциональные требования

### 1. Доступность (Availability)
* Доступность = 99.9%
* Downtime - это период, когда приложение отвечает 5xx-ошибкой
* Downtime в год = 8.76 ч
* Downtime в месяц = 43.2 мин
* Определен такой downtime в связи с потенциальными возможными убытками, понесенными за период простоя. Клиенты не смогут оформлять заказы, потерянная прибыль.
> A = (все_время - время_простоя)/все_время = (30 дней - 43.2 мин) / 30 дней = 99.9
### 2. Надежность (Reliability)
* Кол-во отказов <= 2
> MTBF = (все_время - общ_время_простоя)/кол-во_отказов = (30 дней - 43.2 мин) / 2 = 14.9 дней
### 3. Производительность (Perfomance)
* Latency для (POST /orders)  
> p95 = 200 мс  
> p99 = 400 мс
### 4. Cопровождаемость (Maintainability)
* Покрытие кода тестами >= 80%
* Не более 2 простоев в месяц 
> MTTR = общее_время_восстановления/кол-во_восстановлений = 43.2 мин / 2 = 21.6 мин
### 5. Безопасность (Security)
* Взаимодействие между браузером и сервером должно шифроваться через TLS 1.3
* Чувствительные данные (пароли, токены) должны храниться в хэшированном виде
* Время жизни JWT-токена не более 15 мин, refresh-token - 1 час
### 6. Удобство использования (Usability)
* Создание заказа не более чем за 3 клика
* Адаптивный дизайн на мобильных версиях
* Личный кабинет у пользователя
### 7. Масштабирование (Scalability)
* При росте загрузки CPU > 70% должен добавляться новый экземпляр приложения, а при падении загрузки < 30% удаляться
### 8. Совместимость (Compatibility)
* Должно стабильно работать на последних версиях браузеров: Chrome, Yandex, Edge
* Поддержка мобильных устройств
